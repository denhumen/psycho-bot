# Бот дослідження експресивного письма

Telegram-бот і веб-адмінка для 7-денного дослідження впливу експресивного письма на самопочуття молоді. Повне ТЗ — [SPEC.md](SPEC.md), ухвалені рішення — [DECISIONS.md](DECISIONS.md).

**Що робить:**
- реєстрація за кодом, згода, вибір часу;
- блокова рандомізація A/B у момент «Готовий почати»;
- щоденні інструкції і чек-ін кнопками;
- фінальне посилання на анкету;
- адмінка: прогрес, переписка, експорт, бекапи.

**Один процес** (FastAPI + aiogram long polling + asyncio-планувальник) і **SQLite** на volume. Стан учасника зберігається тільки в БД, тож процес можна перезапустити будь-коли.

```
app/
  main.py          FastAPI, lifespan: міграції → бот (polling) → планувальник; коректна зупинка на SIGTERM
  config.py        змінні оточення (pydantic-settings)
  cli.py           create-admin, backup-now, export, purge-contacts
  db/              моделі SQLAlchemy, сесії SQLite (WAL), міграції Alembic
  domain/          рандомізація, розклад сесій, контент, експорт, бекап, статистика
  bot/             хендлери, клавіатури, sender.py — єдина точка надсилання
  scheduler/       цикл (тік 30 с) і задачі: розсилка, нагадування, закриття, завершення, бекап, дайджест
  admin/           маршрути і шаблони адмінки
content/           усі тексти для учасників (JSON, українською)
tests/             pytest; Telegram замінено фейком
```

## Локальний запуск

Потрібні [uv](https://docs.astral.sh/uv/) і окремий **тестовий** бот. Продакшен-токен локально не використовуйте: два процеси з одним токеном конфліктують за `getUpdates`.

1. **Створіть тестового бота.** У [@BotFather](https://t.me/BotFather): `/newbot`, скопіюйте токен.
2. **Налаштуйте середовище:**
   ```bash
   uv sync
   cp .env.example .env
   ```
   У `.env` заповніть щонайменше:
   ```
   BOT_TOKEN=<токен тестового бота>
   SESSION_SECRET=<python -c "import secrets; print(secrets.token_urlsafe(48))">
   DATABASE_PATH=./data/study.db
   COOKIE_SECURE=false          # локально адмінка працює по http
   CODE_VALIDATION=open         # щоб не завантажувати коди для перевірки
   POST_SURVEY_URL_TEMPLATE=https://docs.google.com/forms/d/e/XXX/viewform?entry.123={code}
   ```
3. **Створіть першого адміна** (пароль запитується інтерактивно, мінімум 10 символів):
   ```bash
   uv run python -m app.cli create-admin --username admin --role owner
   ```
4. **Запустіть:**
   ```bash
   uv run uvicorn app.main:app --port 8000
   ```
   Адмінка відкриється на http://localhost:8000, бот почне відповідати в Telegram. Міграції застосовуються автоматично при старті.

### Прискорений режим (пройти 7 днів за ~15 хвилин)

```
DEV_DAY_MINUTES=2
START_OFFSET_DAYS=0
```

Тепер «день» дослідження триває 2 хвилини: перша інструкція приходить одразу після «Готовий почати», наступні — кожні 2 хвилини. Планувальник тікає раз на 30 с. **У продакшені `DEV_DAY_MINUTES` має бути порожнім**; якщо змінна задана, при старті в лог пишеться WARNING.

### Тести

```bash
uv run pytest
```

Telegram замінено фейком (`tests/fakes.py`), час — замороженим годинником (`app/clock.py`). Мережа не потрібна.

### Підняти локально копію бекапу (для відтворення багів)

1. Візьміть файл `study-YYYY-MM-DD-HHMM.db`: з Telegram-чату бекапів або з адмінки (Бекап → «Завантажити копію БД»).
2. Покладіть його, наприклад, у `./data/repro.db` і в `.env` вкажіть:
   ```
   DATABASE_PATH=./data/repro.db
   BOT_TOKEN=<токен ТЕСТОВОГО бота>
   ```
3. **Перед запуском натисніть паузу або видаліть контакти**, щоб тестовий бот не почав розсилати учасникам із копії. Найпростіше:
   ```bash
   uv run python -m app.cli purge-contacts --confirm
   ```
   Команда видаляє `chat_id` лише в цій локальній копії.
4. Запустіть `uv run uvicorn app.main:app`. Увійти можна тими ж логінами, що й у продакшені: користувачі адмінки лежать у БД.

## Деплой на Railway

### Чому лише 1 репліка

- **Long polling.** Telegram віддає апдейти лише одному споживачеві. Друга репліка отримує `TelegramConflictError`, а апдейти довільно діляться між процесами.
- **SQLite.** Файл БД лежить на volume, який монтується лише до одного контейнера. Друга репліка мала б окрему порожню базу.
- **Планувальник.** Він працює в тому ж процесі, тож дві репліки надіслали б кожне повідомлення двічі.

Railway не монтує один volume до двох деплойментів одночасно. Тому під час редеплою є кілька секунд простою; це нормально: бот і планувальник наздоганяють усе пропущене з БД.

### Кроки

1. **Сервіс із репозиторію.** У [Railway](https://railway.com) створіть **New Project → Deploy from GitHub repo** і оберіть цей репозиторій. Railway знайде `Dockerfile` і збере образ.

2. **Volume.** На полотні проєкту правою кнопкою на сервісі (або `Ctrl/⌘ + K`) → **Add Volume** → mount path **`/data`**.

   Railway монтує volume як root. Контейнер стартує від root лише для того, щоб виконати `chown /data`, а далі запускає застосунок від непривілейованого користувача `app`. Змінна `RAILWAY_RUN_UID` **не потрібна**.

3. **Змінні** (Service → **Variables**):

   | Змінна | Значення |
   |---|---|
   | `BOT_TOKEN` | токен продакшен-бота |
   | `SESSION_SECRET` | 48+ випадкових символів (`python -c "import secrets; print(secrets.token_urlsafe(48))"`) |
   | `DATABASE_PATH` | `/data/study.db` |
   | `POST_SURVEY_URL_TEMPLATE` | посилання на фінальну форму з `{code}` |
   | `CODE_VALIDATION` | `whitelist` (коди завантажуються в адмінці) або `open` |
   | `BACKUP_CHAT_ID` | id **приватного** чату owner для нічних бекапів (див. нижче) |
   | `ADMIN_CHAT_ID` | id чату для щоденного дайджесту (опційно) |
   | `SUPPORT_CONTACT` | контакт підтримки, напр. `@study_support` |
   | `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` | `30`: час між SIGTERM і SIGKILL. **За замовчуванням 0**, і процес убивається, не встигнувши доробити тік. |

   Решта змінних має розумні значення за замовчуванням, див. [.env.example](.env.example). `PORT` Railway підставляє сам. `COOKIE_SECURE` залиште `true`.

4. **Налаштування сервісу** (Service → **Settings**):
   - **Region:** EU West (Amsterdam).
   - **Replicas:** 1. Не збільшувати!
   - **Healthcheck Path:** `/healthz`. Відповідає 200, коли БД доступна і планувальник тікав менше ніж 2 хв тому.
   - **Restart Policy:** On Failure.
   - **Networking → Generate Domain**, щоб отримати адресу адмінки (`https://…up.railway.app`).

5. **Деплой.** Натисніть **Deploy** і дочекайтеся зеленого статусу. У логах мають бути рядки `Застосунок запущено`, `Run polling for bot @…` і `Планувальник запущено`.

6. **Перший адмін через Railway shell:**
   ```bash
   npm i -g @railway/cli     # або brew install railway
   railway login
   railway link              # оберіть проєкт і сервіс
   railway ssh               # відкриється shell у контейнері
   study-cli create-admin --username <логін> --role owner
   ```
   `study-cli` — обгортка над `python -m app.cli`, яка запускає команду від користувача `app`, щоб файли БД не стали власністю root. **Використовуйте саме її**, а не `python -m app.cli`.

   Далі owner створює інших користувачів в адмінці (**Користувачі**).

7. **Перевірка.** Увійдіть в адмінку і (для `whitelist`) завантажте коди на сторінці **Коди**. Потім пройдіть реєстрацію в боті своїм тестовим кодом.

### Як дізнатися `BACKUP_CHAT_ID` / `ADMIN_CHAT_ID`

Напишіть боту [@userinfobot](https://t.me/userinfobot): він покаже ваш id. Це і є `chat_id` приватного чату з вами. Перед цим натисніть **Start** у своєму боті, інакше бот не зможе вам написати.

Для групового чату додайте бота в групу. Id групи має вигляд `-100…`; дізнатися його можна, наприклад, переславши повідомлення з групи в @userinfobot.

> ⚠️ Бекап містить **розподіл за групами** і `chat_id` учасників. `BACKUP_CHAT_ID` має бути чатом лише owner, не спільним чатом команди.

### Оновлення

Пуш у гілку, з якої деплоїть Railway, запускає новий деплой. Міграції БД застосовуються автоматично при старті.

## Відновлення з бекапу

Бекап — звичайний SQLite-файл (`study-YYYY-MM-DD-HHMM.db`). Він приходить щоночі о `BACKUP_TIME` у `BACKUP_CHAT_ID`; також його можна завантажити в адмінці або зробити через `study-cli backup-now --to /data`.

**Railway:**

1. За можливості натисніть **Пауза** на дашборді. Якщо адмінка недоступна, просто продовжуйте.
2. Скопіюйте файл на volume через SFTP (потрібен SSH-ключ, зареєстрований у Railway: `railway ssh` запропонує його додати). Як username підставте домен сервісу:
   ```bash
   scp study-2026-03-10-0300.db <ваш-домен>.up.railway.app@ssh.railway.com:/data/restored.db
   ```
3. У **Variables** змініть `DATABASE_PATH` на `/data/restored.db`. Railway перезапустить сервіс уже на відновленій базі. Старий файл `/data/study.db` лишається недоторканим, на випадок, якщо знадобиться.
4. Перевірте дашборд і, якщо ставили паузу, натисніть **Відновити**. Усе пропущене за час простою планувальник обробить сам: прострочені сесії позначить пропущеними, а не надсилатиме із запізненням.

**Локально:** див. «Підняти локально копію бекапу» вище.

## Як змінити тексти і питання

Усі тексти для учасників лежать у `content/`:

| Файл | Що містить |
|---|---|
| `content/instructions.json` | інструкції письма: групи `A`/`B` × дні `1`–`7` |
| `content/checkin.json` | питання чек-іну: `choice` (варіанти) або `scale` (min..max, кнопки по 5 в ряд) |
| `content/texts.json` | усі інші повідомлення й кнопки бота |

Процес:
1. Відредагуйте JSON (UTF-8).
2. Запустіть `uv run pytest`: тест `test_real_content_is_valid` перевірить файли.
3. Зробіть коміт і пуш, Railway задеплоїть.

Якщо контент невалідний, застосунок **не стартує** і пише зрозумілу помилку з назвою файлу та поля. Тому зламаний текст ніколи не дійде до учасника.

**Правила:**
- **Фігурні дужки — це підстановки.** Дозволені `{support}`, `{time}`, `{date}`, `{url}`, `{day}`, `{today}`, і для деяких ключів вони обов'язкові: наприклад, `final_message` має містити `{url}`.
- **Тексти поза `instructions.json` однакові для обох груп.** Так вимагає дизайн дослідження. Не додавайте в `texts.json` нічого, що натякає на групу.
- **`id` питань і `value` варіантів:** латиниця в нижньому регістрі, цифри, `_`, до 20 символів. Не змінюйте `id` питання посеред дослідження: відповіді прив'язані до нього. Нове питання = новий `id`.
- **Неузгоджені тексти позначено `TODO: погодити`.** Під час старту в лог пишеться попередження з переліком таких місць.

### Форматування і кнопки-посилання

Будь-який текст у `texts.json` можна задати не рядком, а об'єктом. Тоді в ньому працює розмітка Telegram, а під повідомленням з'являються кнопки-посилання:

```json
"welcome_ask_code": {
  "text": "👋 <b>Вітаємо!</b> Це бот дослідження про <i>експресивне письмо</i>.\n\nНадішліть ваш <b>код учасника</b>.",
  "buttons": [
    {"text": "ℹ️ Про дослідження", "url": "https://example.com/about"},
    {"text": "✉️ Написати команді", "url": "https://t.me/your_support"}
  ]
}
```

- **Розмітка:** `<b>жирний</b>`, `<i>курсив</i>`, `<u>підкреслений</u>`, `<s>закреслений</s>`, `<a href="https://...">посилання</a>`, `<code>код</code>`, `<blockquote>цитата</blockquote>`, `<tg-spoiler>спойлер</tg-spoiler>`. Інших тегів Telegram не приймає. Знаки `<`, `>` і `&` як звичайний текст пишіть так: `&lt;`, `&gt;`, `&amp;`.
- **Кнопки:** до 8 штук, кожна в окремому рядку, підпис до 64 символів, `url` починається з `https://`, `http://` або `tg://`. Кнопки-посилання ставляться під кнопками, які бот додає сам (наприклад «Погоджуюсь»), і лишаються після натискання.
- **Обмеження:** звичайним рядком мають лишатися підписи кнопок (`btn_*`) і фрагменти статусу (`status_today_*`), бо вони вставляються в інші тексти чи кнопки. Розширений текст має бути до 4000 символів.
- **Перевірка:** незакритий або непідтримуваний тег, неправильне посилання чи зайве поле — застосунок не стартує і пише, що саме не так. `uv run pytest tests/test_content.py` покаже це до деплою.
- В адмінці такі повідомлення показуються без тегів.

## CLI

У контейнері Railway використовуйте `study-cli <команда>`; локально — `uv run python -m app.cli <команда>`.

| Команда | Що робить |
|---|---|
| `create-admin --username X --role owner\|researcher` | створює користувача адмінки (пароль вводиться інтерактивно) |
| `backup-now [--to PATH]` | копія БД у файл/каталог або (без `--to`) у `BACKUP_CHAT_ID` |
| `export --to DIR` | CSV-експорт (як в адмінці) у каталог; **містить групи** |
| `purge-contacts --confirm` | після завершення дослідження видаляє всі `chat_id` (анонімізація). Просить ввести фразу `ВИДАЛИТИ КОНТАКТИ`. Це єдина операція, що видаляє дані дослідження. |

## Адмінка: ролі

- **researcher:** дашборд, учасники, картка з перепискою, ручні повідомлення, шаблони. **Групи учасників не бачить ніде**, навіть агрегат A/B.
- **owner:** усе те саме, плюс коди, експорт (з групами), бекап, користувачі, пауза розсилки, «Позначити як вибув».

**Захист:**
- логін з argon2;
- підписаний cookie (`HttpOnly`, `Secure`);
- CSRF на кожному POST;
- не більше 5 спроб входу на логін за 15 хвилин.

Текст інструкцій в адмінці не показується: у переписці замість нього стоїть плейсхолдер `📄 Інструкція — день N`.
