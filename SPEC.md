## 0. Контекст

Психологічне дослідження (дипломна робота): вплив експресивного письма на самопочуття молоді в Україні.

Шлях учасника:
1. Заповнює Google-форму з первинним скринінгом. Отримує/створює **унікальний код**.
2. Переходить у Telegram-бот, реєструється за кодом, дає згоду, обирає час нагадувань, натискає «Готовий почати».
3. У цей момент бот **випадково** призначає його в групу **A** або **B** (блокова рандомізація, блоки по 4).
4. Протягом **7 днів** щодня в обраний час отримує інструкцію письма (своєї групи), пише **офлайн** (тексти боту НЕ надсилає), потім проходить короткий чек-ін кнопками.
5. Після 7-го дня отримує посилання на фінальну Google-форму (з підставленим кодом).

Виконавці дослідження працюють через веб-адмінку: бачать прогрес учасників, пишуть їм повідомлення через бота, експортують дані.

Масштаб: ~100–150 учасників, ~3–4 місяці роботи. Один інстанс.

## 1. Інваріанти (порушувати не можна)

1. **Прихованість розподілу.** Послідовність груп ніде не показується в адмінці: ні перегляду, ні редагування. Група конкретного учасника не показується ніде, крім CSV-експорту (тільки роль `owner`).
2. **Без ручних змін розподілу.** Немає жодного способу змінити групу учасника чи наступний слот через UI/API.
3. **Атомарне призначення.** Два одночасні учасники ніколи не отримують один слот.
4. **Безпечний рестарт.** Перезапуск процесу в будь-який момент не губить і не дублює повідомлення, не ламає діалог учасника. Стан учасника береться з БД, не з пам'яті.
5. **Дані тільки додаються.** Відповіді чек-інів і повідомлення — тільки `INSERT`. Зміни статусів логуються в `events`. Жодних `DELETE` даних дослідження з коду застосунку (виняток — явна CLI-команда очищення контактів після завершення дослідження).
6. **Однаковий контакт для обох груп.** Усі автоматичні тексти, крім самих інструкцій письма, однакові для A і B. Шаблони нагадувань — без прив'язки до групи.
7. **Мінімум персональних даних.** Не зберігати ім'я, username, телефон. Тільки `chat_id` в окремій таблиці `contacts`.
8. **Зміст інструкцій не видно в адмінці.** У переписці учасника замість тексту інструкції показується плейсхолдер `📄 Інструкція — день N`.

## 2. Стек

| Шар | Технологія |
|---|---|
| Мова | Python 3.12 |
| Залежності | `uv` + `pyproject.toml` |
| Бот | aiogram 3, **long polling** |
| Веб / адмінка | FastAPI + Jinja2 (серверний рендер), HTMX дозволено для оновлення чату/лічильників, без SPA і без окремого фронт-білду. Простий CSS (напр. Pico.css з CDN), адаптивно під телефон |
| БД | SQLite (WAL) через SQLAlchemy 2 (async) + aiosqlite |
| Міграції | Alembic, `upgrade head` автоматично при старті |
| Конфіг | pydantic-settings, змінні оточення |
| Паролі | argon2 (`argon2-cffi`) |
| Сесії адмінки | підписані cookie (Starlette `SessionMiddleware`) + CSRF-токен на всіх POST |
| Тести | pytest + pytest-asyncio |
| Деплой | Dockerfile, Railway (1 сервіс + volume у `/data`) |
| Часова зона | `Europe/Kyiv` через `zoneinfo`; у БД усі часи в UTC |

**Один процес:** FastAPI (uvicorn) у `lifespan` запускає: aiogram polling, планувальник (asyncio-цикл), і коректно зупиняє їх на SIGTERM.

**Не використовувати:** aiogram `MemoryStorage`/FSM для бізнес-стану, Redis, Celery, APScheduler, окремий сервер БД, webhook.

## 5. Модель даних

Усі часові поля — UTC (`datetime` з tz). Усі таблиці мають `created_at`.

**participants**
- `id` PK
- `code` UNIQUE (нормалізований: trim + upper)
- `status`: `registered` → `consented` → `active` → `completed`; або `declined` (не погодився), `withdrawn` (вийшов)
- `reminder_time` (`HH:MM`, nullable до вибору)
- `start_date` (date, nullable до старту)
- `consented_at`, `randomized_at`, `completed_at`, `withdrawn_at` (nullable)
- `post_survey_sent_at` (nullable)
- `last_activity_at`
- `bot_blocked` bool (учасник заблокував бота)

**contacts** — окремо, щоб видалити після дослідження
- `participant_id` PK/FK
- `chat_id` UNIQUE

**allowed_codes** (для `CODE_VALIDATION=whitelist`)
- `code` PK, `uploaded_at`, `uploaded_by`

**allocation_slots**
- `slot_no` PK (0, 1, 2, …)
- `block_no`
- `group` (`A`/`B`)
- `participant_id` UNIQUE nullable
- `assigned_at` nullable

**sessions** — 7 рядків на учасника, створюються в момент рандомізації
- `id` PK
- `participant_id`, `day` (1–7), UNIQUE(participant_id, day)
- `scheduled_for` (UTC, обчислено з `start_date + day-1` і `reminder_time` у Києві — враховувати перехід на літній/зимовий час)
- `deadline` = `scheduled_for` наступного дня (для дня 7 — `scheduled_for + 24h`)
- `sent_at`, `reminder_sent_at`, `completed_at`, `missed_at` (nullable)

**checkin_answers** — тільки INSERT
- `id`, `session_id`, `question_id`, `value` (str), `answered_at`
- UNIQUE(session_id, question_id) — перша відповідь фіксується, повторні натискання ігноруються

**messages** — вся переписка, тільки INSERT
- `id`, `participant_id`
- `direction`: `in` / `out`
- `kind`: `instruction`, `checkin`, `auto_reminder`, `manual`, `system`, `participant_text`
- `sender_admin_id` nullable (для `manual`)
- `text` (для `instruction` у адмінці не показувати, див. інваріант 8)
- `telegram_message_id`, `session_day` nullable
- `read_by_admin_at` nullable (для `in`)

**reminder_templates**
- `id`, `title`, `text`, `is_active`

**admin_users**
- `id`, `username` UNIQUE, `password_hash`, `role` (`owner` / `researcher`), `is_active`, `last_login_at`

**events** — аудит
- `id`, `at`, `actor` (`system` / `bot` / `admin:<id>`), `participant_id` nullable, `type`, `payload` (JSON)
- Типи щонайменше: `status_changed`, `randomized` (без групи в payload!), `admin_login`, `admin_message_sent`, `scheduler_paused`, `scheduler_resumed`, `codes_uploaded`, `export_downloaded`, `backup_sent`, `send_failed`.

**settings** — key/value
- `scheduler_paused` (bool)
- `last_backup_at`

## 6. Рандомізація

- **Генерація:** при першому старті, якщо `allocation_slots` порожня, згенерувати `ALLOCATION_INITIAL_BLOCKS` блоків розміру `ALLOCATION_BLOCK_SIZE`; кожен блок — рівно половина A, половина B, порядок перемішаний через `secrets.SystemRandom`. Без seed. Послідовність існує лише в БД.
- **Дозаповнення:** якщо вільних слотів < 1 блоку — автоматично згенерувати ще блоки тим самим способом (append).
- **Призначення** (`allocate(participant_id) -> group`): у транзакції `BEGIN IMMEDIATE`: взяти мінімальний `slot_no` з `participant_id IS NULL`, записати учасника, `assigned_at`; commit. Додатково обгорнути `asyncio.Lock`. Ідемпотентно: якщо учасник уже має слот — повернути його.
- Після призначення: статус `active`, `start_date = today_kyiv + START_OFFSET_DAYS`, створити 7 `sessions`.
- **Тести (обов'язково):**
  - у будь-який момент при послідовному призначенні |A − B| ≤ 2;
  - після кожних 4 призначень |A − B| = 0;
  - 50 конкурентних викликів `allocate` → 50 різних слотів, без помилок;
  - повторний `allocate` того самого учасника повертає ту саму групу.

## 7. Бот: флоу учасника

### Загальні правила
- **Стан учасника визначається з БД** (`participants.status` + наявність сесій/відповідей), не з FSM.
- **Кожна inline-кнопка самодостатня:** `callback_data` містить усе потрібне, напр. `ci:{session_id}:{question_id}:{value}`, `time:{HH:MM}`, `consent:yes`. Обробник перевіряє актуальність (статус, дедлайн) і відповідає `answer_callback_query` у будь-якому разі.
- Після відповіді на кнопку — редагувати повідомлення: показати обраний варіант, прибрати клавіатуру.
- Усі тексти — з `content/texts.json`, жодних хардкод-рядків українською в коді.
- Усі вихідні повідомлення — через `bot/sender.py` (логування в `messages`, обробка `RetryAfter`, `TelegramForbiddenError` → `bot_blocked = true` + event).
- Повідомлення > 4096 символів розбивати по абзацах.

### Кроки

1. **`/start` або `/start <CODE>`** (deep link)
   - Якщо цей `chat_id` вже прив'язаний → показати поточний статус і що далі (див. `/status`).
   - Якщо код у deep link → одразу перевірити (крок 2). Інакше попросити ввести код.
2. **Перевірка коду** (будь-який текст від незареєстрованого chat_id трактується як код)
   - нормалізація: trim, upper;
   - не відповідає `CODE_REGEX` → «Невірний формат, спробуйте ще»;
   - `whitelist` і коду немає в `allowed_codes` → «Код не знайдено. Перевірте або напишіть {SUPPORT_CONTACT}»;
   - код уже прив'язаний до іншого chat_id → відмова + event `code_conflict` (видно в адмінці);
   - успіх → створити `participant` (`registered`) + `contact`, показати текст інформованої згоди з кнопками «Погоджуюсь» / «Не погоджуюсь».
3. **Згода**
   - «Не погоджуюсь» → `declined`, подяка, більше нічого не надсилати.
   - «Погоджуюсь» → `consented`, запропонувати вибір часу (кнопки з `REMINDER_TIME_OPTIONS`).
4. **Час** → зберегти `reminder_time`, показати пояснення (7 днів, щодня о HH:MM, тексти не надсилати боту, `/stop` для виходу) і кнопку **«Готовий почати»**.
5. **«Готовий почати»** → рандомізація (розділ 6) → однакове для обох груп повідомлення: «Перша інструкція прийде {дата} о {час}».
   - Учасник, що не натиснув кнопку, групу не отримує.
6. **Щоденна сесія** (надсилає планувальник)
   - Текст інструкції для `(group, day)` з `instructions.json` + кнопка «Пройти коротке опитування».
   - Чек-ін: питання з `checkin.json` по одному, кожне з inline-кнопками. Коли відповіді на всі питання є → `sessions.completed_at`, подяка (однаковий текст).
   - Натискання після `deadline` → «Час для цього дня минув», нічого не записувати.
7. **Після дня 7** (коли сесія 7 завершена або прострочена) → статус `completed`, надіслати фінальне повідомлення з посиланням `POST_SURVEY_URL_TEMPLATE` (`{code}` URL-encoded), `post_survey_sent_at`.

### Команди
- `/status` — день N з 7, чи пройдено сьогодні, час нагадувань.
- `/time` — змінити час нагадувань; перераховує `scheduled_for`/`deadline` тільки для ще не надісланих сесій.
- `/stop` — підтвердження кнопками → `withdrawn`, подяка, жодних автоматичних повідомлень далі. Дані не видаляються.
- `/help` — короткий опис + `SUPPORT_CONTACT`.

### Довільний текст від зареєстрованого учасника
- Зберегти в `messages` (`in`, `participant_text`, непрочитане).
- Відповісти один раз на 6 годин: «Ваше повідомлення передано команді дослідження». Якщо статус `active` — додати нагадування, що тексти письма надсилати не потрібно.
- Фото/голосові/файли: не зберігати вміст, записати `[медіа: тип]`, відповісти що бот приймає лише текст.

## 8. Планувальник

Один asyncio-цикл, тік кожні 30 с. Кожна задача **ідемпотентна** і спирається тільки на БД. Помилка в одній задачі не зупиняє інші і цикл (логувати, event `send_failed`).

Якщо `settings.scheduler_paused = true` — **жодних** автоматичних дій з учасниками (не надсилати, не закривати сесії). Після зняття паузи — все пропущене обробляється наступним тіком. Бекап і дайджест працюють і під час паузи.

Задачі:
1. **send_due** — сесії з `scheduled_for <= now`, `sent_at IS NULL`, `deadline > now`, учасник `active`, не `bot_blocked` → надіслати інструкцію, `sent_at`. Сесії, у яких `deadline` минув до надсилання (довгий простій), — не надсилати, позначити `missed_at`, event.
2. **auto_reminders** — якщо `AUTO_REMINDER_AFTER_HOURS > 0`: сесії надіслані ≥ N год тому, не завершені, `reminder_sent_at IS NULL`, дедлайн не минув → один нейтральний текст з `texts.json` (однаковий для всіх).
3. **close_expired** — `deadline <= now`, не завершені, не `missed` → `missed_at`.
4. **finish_participants** — учасники `active`, у яких сесія 7 закрита → крок 7 флоу.
5. **nightly_backup** — раз на добу о `BACKUP_TIME`: `sqlite3` backup API у тимчасовий файл → `sendDocument` у `BACKUP_CHAT_ID` з підписом (дата, кількість учасників) → `settings.last_backup_at`. «Раз на добу» визначати через `last_backup_at`, щоб рестарт не дублював і не пропускав.
6. **daily_digest** — раз на добу о `DIGEST_TIME` у `ADMIN_CHAT_ID`: тільки агрегати (зареєстровано / активні / завершили / вийшли; вчора: надіслано, пройдено, пропущено; непрочитаних повідомлень). Без груп.

Надсилання масових повідомлень — з паузою ~50 мс між ними, обробка `RetryAfter`.

## 9. Адмін-панель

Логін за username/паролем. Створення першого користувача: `python -m app.cli create-admin --username X --role owner` (пароль інтерактивно). Далі `owner` створює інших в UI.

Ролі:
- `researcher` — дашборд, учасники, картка, повідомлення, шаблони.
- `owner` — усе вище + коди, експорт, бекап, користувачі, пауза.

Захист: CSRF на всіх POST, ліміт спроб логіну (5 на 15 хв на username), cookie `HttpOnly` + `Secure`, усі сторінки крім `/login` і `/healthz` — тільки для залогінених.

### Сторінки

**Дашборд `/`**
- Лічильники за статусами.
- Рандомізовано: A — n, B — n; завершили: A — n, B — n (тільки агрегати).
- Сьогодні: інструкцій надіслано / чек-інів пройдено / очікують.
- Непрочитані повідомлення (посилання).
- Конфлікти кодів, заблоковані боти.
- Останній бекап (час), статус паузи + кнопка «Пауза / Відновити» (owner, з підтвердженням).

**Учасники `/participants`**
- Таблиця: код, статус, день N/7, прогрес (7 клітинок: ● пройдено, ✕ пропущено, ○ надіслано-очікує, · ще не надіслано), остання активність, непрочитані.
- **Колонки групи немає.**
- Фільтри: статус; «не пройшли сьогодні»; «пропустили 2+ дні поспіль»; «є непрочитані»; «зареєструвались, але не стартували»; пошук за кодом.

**Картка учасника `/participants/{code}`**
- Статус, дати, час нагадувань, `bot_blocked`.
- Таймлайн 7 днів: заплановано, надіслано, нагадування, завершено/пропущено, відповіді чек-іну.
- Чат: уся переписка хронологічно; інструкції — плейсхолдер `📄 Інструкція — день N`; ручні повідомлення з іменем автора; вхідні непрочитані підсвічені, при відкритті картки позначаються прочитаними.
- Форма «Написати»: textarea + випадайка шаблонів (підставляє текст, можна редагувати) → надсилається через бота, лог у `messages` (`manual`, `sender_admin_id`) і `events`. Недоступно для `withdrawn`/`declined` (показати попередження).
- Без кнопок зміни групи чи статусу (крім `owner`: «Позначити як вибув» з підтвердженням → `withdrawn` + event).

**Шаблони нагадувань `/templates`** — CRUD.

**Коди `/codes`** (owner) — завантаження CSV / вставка списку кодів (по одному в рядку), нормалізація, звіт: додано / дублікати / невалідні. Показ: всього, використано, вільних.

**Експорт `/export`** (owner) — ZIP з CSV:
- `participants.csv` (code, group, status, усі дати, reminder_time),
- `sessions.csv`,
- `checkin_answers.csv` (широкий формат теж: один рядок = учасник × день, колонки = питання),
- `messages.csv` (без тексту інструкцій),
- `events.csv`.
Кожне завантаження → event `export_downloaded`.

**Бекап `/backup`** (owner) — кнопка «Завантажити копію БД» (через sqlite backup API, не копіювати живий файл напряму) і «Надіслати бекап у Telegram зараз».

**Користувачі `/users`** (owner) — створення, деактивація, скидання пароля.

**`/healthz`** — 200 якщо БД доступна і цикл планувальника робив тік < 2 хв тому.

## 10. Контент (JSON)

Валідувати при старті (pydantic). Невалідний контент → застосунок не стартує з чіткою помилкою. Зміна контенту = коміт + деплой.

`content/instructions.json`
```json
{
  "A": { "1": "TODO текст інструкції A день 1", "2": "...", "...": "...", "7": "..." },
  "B": { "1": "TODO текст інструкції B день 1", "...": "...", "7": "..." }
}
```
Перевірка: обидві групи, дні 1–7, непорожні.

`content/checkin.json`
```json
{
  "questions": [
    { "id": "did_write", "type": "choice", "text": "Чи виконали ви сьогоднішнє завдання?",
      "options": [ {"value": "yes", "label": "Так"}, {"value": "partly", "label": "Частково"}, {"value": "no", "label": "Ні"} ] },
    { "id": "mood", "type": "scale", "text": "Як ви почуваєтесь зараз? 1 — дуже погано, 10 — дуже добре", "min": 1, "max": 10 }
  ]
}
```
Типи: `choice`, `scale` (кнопки min..max, по 5 в ряд). Інших типів не треба. Плейсхолдерні питання — вище; виконавці замінять.

`content/texts.json` — усі UI-тексти бота: привітання, запит коду, помилки коду, інформована згода, пояснення після вибору часу, підтвердження старту, кнопки, подяка після чек-іну, авто-нагадування, фінальне повідомлення, `/help`, `/stop`, відповідь на довільний текст. Заповни розумними нейтральними українськими текстами з позначкою `TODO: погодити` там, де потрібне рішення дослідників (згода, контакти).

## 12. Надійність і деплой

- Міграції Alembic при старті до запуску бота.
- SQLite: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`.
- Graceful shutdown: на SIGTERM зупинити polling, дочекатися поточного тіку планувальника.
- `TelegramConflictError` при старті (старий інстанс ще поллить під час деплою) → ретрай з backoff до 60 с, не падати.
- Логи в stdout (JSON або читабельний формат з рівнями), без токенів і chat_id у логах.
- **Тільки 1 репліка.** Задокументувати в README, чому (polling + SQLite).
- `Dockerfile`: slim-образ, non-root, `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
- `README.md`:
  - локальний запуск з тестовим ботом (окремий `BOT_TOKEN` від BotFather);
  - як підняти локально з копією бекапу (для відтворення багів);
  - деплой на Railway покроково: створити сервіс з GitHub-репо, додати volume з mount path `/data`, змінні оточення, регіон EU West, 1 репліка, створення першого адміна через Railway shell;
  - як відновитися з бекапу;
  - як змінити тексти/питання.

## 13. Тести (мінімум)

- Рандомізація: баланс ≤ 2 в будь-який момент, = 0 після кожного блоку, конкурентність, ідемпотентність, дозаповнення.
- Сесії: правильні `scheduled_for` у UTC для різних `reminder_time`, включно з переходом на зимовий/літній час у Києві; `/time` змінює тільки ненадіслані.
- Планувальник: повторний тік не дублює надсилання; пауза блокує надсилання; після простою прострочені сесії → `missed`, а не надсилаються; бекап не дублюється після рестарту.
- Чек-ін: повторне натискання не створює другу відповідь; натискання після дедлайну ігнорується; сесія завершується після всіх питань.
- Реєстрація: whitelist, конфлікт коду, повторний `/start`.
- Адмінка: жодна HTML-сторінка не містить групу учасника (тест рендерить сторінки і перевіряє); `researcher` не має доступу до експорту/кодів/бекапу; CSRF.
- Контент: невалідний JSON → зрозуміла помилка старту.

Telegram API в тестах — мокати (фейковий `Bot`/sender).

## 15. Критерії готовності
- `docker build` проходить; `pytest` зелений.
- Локально з тестовим ботом проходиться повний шлях: код → згода → час → старт → (з прискореним часом через env/фікстуру) 7 сесій з чек-інами → фінальне посилання.
- В адмінці видно прогрес, працює ручне повідомлення і відповідь учасника з'являється в чаті.
- Рестарт процесу посеред чек-іну не ламає діалог.
- Нічний бекап приходить у Telegram, і з нього можна підняти застосунок.
- README достатній, щоб задеплоїти на Railway без додаткових питань.
